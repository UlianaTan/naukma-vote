# Як працюємо з репозиторієм

1. Створіть Issue з метою, відповідальним і критеріями готовності.
2. Перед новою задачею: `git switch main`, потім `git pull --ff-only`.
3. Створіть гілку: `git switch -c feat/task-name`. Для виправлень — `fix/`,
   документації — `docs/`, інфраструктури — `chore/`.
4. Внесіть зміни та виконайте перевірки відповідного компонента.
5. Перегляньте `git diff` і `git status`; додавайте лише потрібні файли.
6. Зробіть commit, опублікуйте гілку через `git push -u origin branch-name`.
7. Відкрийте Pull Request у main, заповніть шаблон, запросіть reviewer.
8. Після успішних перевірок та review іншого учасника використайте Squash merge.

Не робимо прямі push у main, force push у main або зміни чужих гілок.
Ці правила організаційні, доки власниця репозиторію не увімкне захист у GitHub.

## Definition of Done

- Виконані критерії задачі; PR пов'язаний з Issue.
- Є review щонайменше одного іншого учасника.
- Підключені перевірки проходять; перевірки компонента описані в PR.
- Документація відповідає змінам; секретів і персональних даних немає.
- Зміни авторизації, голосування й анонімності перевірені разом із QA.
- Для UI перевірено мобільний екран, завантаження, порожні стани та помилки.
- Якщо задача завершує етап роботи, додано звіт у `docs/handoff/` і посилання на нього в PR або Issue.

Зміни API погоджують backend і обидва frontend-розробники до злиття.
Немає окремого Team Lead: DevOps організовує sync, кожен веде свої задачі.

## Звіти після завершення етапу

Кожен учасник, незалежно від ролі, залишає короткий звіт після завершення
узгодженого етапу: наприклад, каркаса застосунку, авторизації, прототипу,
раунду тестування або налаштування staging. Це також потрібно, коли результат
передається іншому учаснику. Окремий звіт на кожен commit не потрібен.

1. Скопіюйте [шаблон звіту](docs/handoff/TEMPLATE.md) в новий файл у `docs/handoff/`.
2. Назвіть файл `YYYY-MM-DD-role-stage.md`, наприклад `2026-09-25-devops-ci-setup.md`.
3. Вкажіть автора, завершений етап, зроблене, перевірки, незавершене та наступні кроки.
4. Додайте звіт до PR, який завершує етап, або окремим документаційним PR,
   якщо етап не має змін коду. Залиште посилання у відповідній задачі.
5. Якщо інший учасник має продовжити роботу, вкажіть його роль та що саме передаєте.

Етап вважається завершеним після додавання звіту. Якщо є блокери чи невиконані
критерії, позначте статус «частково завершено» або «заблоковано», а не «завершено».
У звітах не публікуємо паролі, токени, реальні голоси чи персональні дані студентів.
Деталі та приклади — у [правилах звітів](docs/handoff/README.md).
