# Запуск, міграції та підготовка staging

Staging-адреси вже створені в Render, БД — Neon PostgreSQL 18. Це не означає,
що конфігурація або реальний Google-вхід перевірені. Налаштування зовнішніх
сервісів і міграції реальної Neon-БД виконуються лише окремою погодженою дією.

## Єдиний порядок для local, staging і production

Backend **не створює й не змінює таблиці під час запуску**, включно з local.
Усі зміни схеми — Alembic. PostgreSQL 18 є основною БД для розробки й деплою;
SQLite/create_all залишаються лише ізольованими тестовими fixtures.

З кореня репозиторію, з активованим Python-середовищем і налаштованим DATABASE_URL:

```sh
python -m alembic current
python -m alembic heads
# Після перевірки стану БД та дозволу на конкретне оновлення:
python -m alembic upgrade head
python -m alembic check
python -m uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

`upgrade head` створює таблиці в новій порожній БД або виконує лише невиконані
міграції в наявній. Повторний запуск на актуальній схемі не створює дані повторно.
`alembic check` порівнює підтримувані Alembic елементи схеми з моделями;
це не перевірка всіх даних або повного сценарію сайту.

## Наявна БД: спочатку перевірка, потім зміни

1. Підтвердити, що DATABASE_URL вказує саме на потрібне середовище. Не друкувати URL із паролем.
2. Перевірити таблиці, `alembic_version`, `alembic current` та історію міграцій.
3. Якщо таблиці існують, а історії Alembic немає або вона не відповідає схемі,
   зупинитися й порівняти фактичну структуру. Не виконувати `stamp head` або
   `upgrade` навмання. Потрібний окремий план приведення БД до відомої версії.
4. Для важливих даних підготувати резервну копію й можливість відновлення в іншій БД.
   Для порожньої одноразової тестової БД копія не потрібна.
5. Виконати погоджені міграції, перевірити `alembic current` і `alembic check`.
6. Запустити backend, перевірити `/health/ready`, потім користувацький сценарій.

Міграція `9f5d3b8c1a20` зупиняється, якщо є різні користувачі з однаковим
нормалізованим email. Вона не об’єднує акаунти й не змінює їхні ID.
Попередня `7d3b9f1a5c82` нормалізує email допуску, прибирає повторні записи
допуску й перейменовує дублікати кандидатів. Ці зміни потрібно врахувати при
перевірці старих даних; відкат схеми не відновлює початкові значення автоматично.

## Налаштування staging і production

Обидва середовища відмовляються стартувати з небезпечною конфігурацією:

- `APP_ENV=staging` або `production`; невідомі значення відхиляються.
- `DATABASE_URL` — окрема PostgreSQL через `postgresql+asyncpg`, без локальних
  дефолтних облікових даних. Для Neon використовуйте рекомендоване ним TLS-підключення.
- `ALLOW_MOCK_AUTH=false`; тестовий вхід поза local заборонений.
- `SESSION_SECRET` — окремий випадковий секрет щонайменше 32 байти.
- `FRONTEND_ORIGIN` — точний HTTPS origin без шляху, query або wildcard.
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — непорожні значення.
- `GOOGLE_REDIRECT_URI` — точний HTTPS URL з `/api/auth/google/callback`.
  Для staging: `https://naukma-vote-backend-staging.onrender.com/api/auth/google/callback`.
- `ALLOWED_EMAIL_DOMAIN=ukma.edu.ua` — точний домен підтвердженої Google-адреси; Workspace не обов’язковий.
- `ELECTION_CLOSER_ENABLED=true`; інтервал і строки сесії — додатні числа.
- `SESSION_COOKIE_SAMESITE` — `none` для різних site або `lax`/`strict`, якщо це
  відповідає розміщенню та перевірено в браузері. Поза local cookies завжди Secure.

Ці перевірки підтверджують формат і наявність параметрів. Правильність Google
секретів, доступів до Neon та браузерних cookies перевіряється окремо на staging.
Секрети зберігаються в environment сервісу, не в Git або повідомленнях чату.

## Послідовність розгортання Render

1. Встановити backend-залежності: `python -m pip install -r backend/requirements.txt`.
2. Виконати Alembic **одним окремим кроком перед запуском нової версії**.
   Якщо тариф/налаштування сервісу не мають такого кроку, використати окрему
   погоджену команду або job. Не запускати міграції автоматично в кожному worker.
3. Запустити `python -m uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port "$PORT"`.
4. Налаштувати `/health/ready` як перевірку готовності й перевірити результат.
5. Для frontend перевірити `VITE_API_BASE_URL`, збирання та відкриття вкладених маршрутів.

Під час startup backend лише читає версію Alembic і перевіряє необхідні таблиці
та колонки. Без міграцій або з недоступною БД запуск завершується поясненням.
`/health` і `/health/live` перевіряють процес. `/health/ready` повертає 503,
якщо БД недоступна або перевірка схеми не пройшла. Це не перевірка Google-входу.

## Приватність журналів

Стандартний запуск через Uvicorn підключає фільтр до наявних обробників журналів:
query у access log не записується (зокрема OAuth `code`/`state`), SQL-діагностика
й тексти винятків із параметрами приховуються. Залишаються шлях, HTTP-статус і
тип помилки; SQLAlchemy також має `hide_parameters=True`.
Сервіс не журналює cookies, заголовки авторизації, тіла запитів і вибір користувача.

Фільтр стосується журналів застосунку/Uvicorn. Журнали reverse proxy, Render,
Neon та сторонніх сервісів потрібно перевірити окремо. Зміна logging-конфігурації
після імпорту застосунку також потребує збереження фільтра.
Діагностичний вивід ручних CLI-команд міграцій не є публічним журналом сервісу:
його не можна публікувати без перевірки на чутливі дані.

## Відкат і підтвердження готовності

Перед релізом визначити сумісність попереднього коду з новою схемою. Якщо схема
сумісна, можна повернути попередню версію коду без downgrade БД. Інакше потрібний
окремий план; не запускати downgrade автоматично. Відновлення копії спершу
перевіряється в окремій БД, з урахуванням даних, що з’явилися після копіювання.

Локальні тести та зелений CI не підтверджують готовність staging. Окремо потрібні
реальний Google-вхід, refresh/logout, cookies і повний цикл тестового голосування.
