## Дефекти

| ID | Пріоритет | Назва |
|---|---|---|
| D-1 | Critical | Адмін-API доступне без автентифікації |
| D-2 | Critical | Адмін-панель у frontend відкривається без входу |

**D-1. Адмін-API доступне без автентифікації**

- Кроки: 1) надіслати `GET /admin/elections` без заголовків; 2) повторити із заголовком `X-User-Id` звичайного виборця; 3) аналогічно для `POST /admin/elections`, `/activate`, `/close`, `/audit`, `/results/export.csv`.
- Фактично: у mock-режимі відповідь успішна (не 401/403) для всіх.
- Очікувано: 401 без автентифікації, 403 для користувача без ролі організатора.
- Причина (за кодом): `get_current_user` в `app/core/dependencies.py` не читає `X-User-Id` і завжди повертає тестового адміністратора; відмова за роллю не спрацьовує для автоматично створеного mock-адміністратора. Це наявне обмеження mock-режиму, а не зміна, внесена цим PR; очікування 401/403 стосується майбутньої справжньої авторизації.
- Докази: тести `test_BUG1_admin_api_requires_authentication` і `test_BUG1_voter_cannot_use_admin_api` (позначені `expectedFailure`; після реалізації Auth вони «несподівано пройдуть», і треба буде прибрати декоратор).
- Статус: відкритий, залежить від Backend Auth. Перевірка staging не виконувалась; недоступність сервісу цим звітом не підтверджена. Дефект підтверджено автоматичними тестами на локальному застосунку з mock-авторизацією.
- Примітка: у production без Auth-модуля адмін-API відповідає 401 (перевірено тестом `test_mock_auth_disabled_returns_401_everywhere`), тобто там адмінка поки не працює взагалі.

**D-2. Адмін-панель у frontend відкривається без входу**

- Кроки: у режимі інкогніто відкрити `http://localhost:5173/admin`.
- Фактично: сторінка відкривається, вхід не вимагається.
- Очікувано: перенаправлення на вхід або відмова в доступі.
- Статус: відкритий; обмеження на frontend доповнює, але не замінює серверну перевірку (D-1).

## Спостереження (не дефекти або потребують підтвердження)

- **O-1.** Запит до виборчих ендпоінтів без `X-User-Id` обробляється як дефолтний тестовий студент. Тому сценарій «голос без сесії» неможливо перевірити до появи Auth.
- **O-2.** За аналізом коду (не відтворювалось): mock-авторизація створює нового користувача при першому запиті, тож паралельні перші запити нового користувача можуть конфліктувати за унікальним email. Для production не актуально, але на staging з mock може дати 500.
- **O-3.** У `docstring` файлу `tests/test_pg_concurrency.py` вказано PostgreSQL 16, а CI і README використовують 18.
- **O-4.** Під час написання тестів SQLite некоректно працював із UUID виду `000003e9-0000-…` (рядок схожий на число в експоненційному записі). Це артефакт тестового середовища, у тестах такі UUID не використовуються. На PostgreSQL (нативний UUID) не очікується.
- **O-5.** У переглянутому коді (`app/main.py`) не знайдено rate limiting і CSRF-захисту, які описані в README як заплановані. Перевірити їх можна лише після реалізації.
- **O-6.** Розділення таблиць явки й бюлетенів не гарантує повну анонімність (README це визнає). Автоматично перевірено лише схему даних і відповіді API. Кореляція записів за часом і порядком вставки, а також прямий доступ до БД не перевірялись.

## Як використати результат

1. Запустити тести з каталогу `backend`: `../.venv/bin/python -m unittest discover -s tests -v`.
2. Для паралельних тестів задати `TEST_DATABASE_URL` на окрему PostgreSQL 18 з назвою БД, що закінчується на `_test` або `_ci` (у CI вже налаштовано).
3. Коли Backend Auth реалізує авторизацію, прибрати `@unittest.expectedFailure` з двох тестів `BUG1`; вони мають стати зеленими.
4. Після змін у логіці голосування, життєвому циклі, результатах чи CSV повторити запуск як регресію.

## Незавершене, обмеження та блокери

- **Заблоковано відсутністю Auth:** вхід і вихід реальним акаунтом, відмова чужому домену, закінчення сесії, перевірка прав організатора, rate limiting і CSRF, голос без сесії, наскрізна авторизація на staging.
- **Тиждень 7:** сценарії й тестові акаунти для користувацького тестування не підготовлені. Підготовка чернеток сценаріїв не заблокована Auth і залишається окремою задачею QA; реальні акаунти та перевірка входу потребують інтеграції Auth.
- **Тиждень 8 (не виконано):** тестування зі студентами, фіксація браузерів, реєстрація зауважень і регресія критичного шляху.
- **Тиждень 9 (не виконано):** фінальна регресія, release checklist, перевірка production після деплою. За `docs/voting-core-operations.md` production-запуск навмисно неможливий, доки не підключено Auth-модуль: застосунок не стартує з mock-авторизацією. З production-чекліста backend на QA припадають: звірка підрахунку на окремому тестовому голосуванні, перевірка закриття тестового голосування таймером, `app.cli.validate_data` без критичних проблем, зелені `unittest` і `tests/test_pg_concurrency.py` на тестовій PostgreSQL.
- **Не перевірялось:** технічні логи сервера, мобільний вигляд і доступність, продуктивність, повна анонімність на рівні БД, запуск `app.cli.validate_data`, відновлення з резервної копії.
- **Блокери релізу:** відкриті critical-дефекти D-1 і D-2; відсутня реальна авторизація.
